# P0-06 — Textes SEO et assistant alignés sur la recherche de stage

## Ce qui a été fait
Quatre chaînes de texte modifiées, sans toucher à la logique :
- `src/pages/_document.page.tsx` : méta-description par défaut (celle que voient les robots qui n'exécutent pas le JavaScript).
- `src/lib/assistant-context.ts` : statut annoncé par l'assistant quand le profil est « Disponible » → recherche d'un stage de fin d'études de 6 mois en IA appliquée & MLOps à partir de février 2027.
- `src/pages/ProjectsPage.tsx` et `src/pages/BlogPage.tsx` : descriptions SEO des pages Projets et Blog.
`npm run build` réussi avant le push (avec des variables Supabase factices passées seulement dans l'environnement du shell, car aucun `.env` n'existe en local). Après déploiement, la nouvelle méta-description est servie par https://francisitoua.vercel.app (vérifié le 11/10/2026).

## Pourquoi ce choix plutôt que l'alternative courante
L'alternative aurait été de rendre ces textes administrables (nouveaux champs dans Supabase et dans l'administration). C'est plus souple, mais cela touche au schéma de données, à l'administration et au rendu : beaucoup de risque pour quatre phrases qui changent rarement. Modifier les chaînes en dur, avec un build vérifié, est le changement minimal.

## 5 questions d'entretien
1. **Pourquoi une méta-description par défaut dans `_document` alors que `SEOHead` la met déjà à jour ?**
   `SEOHead` agit côté navigateur, après exécution du JavaScript. Les robots et les aperçus de liens qui lisent seulement le HTML initial voient la valeur de `_document`. Elle doit donc porter le positionnement elle aussi.
2. **Pourquoi l'assistant devait-il changer de phrase ?**
   Il construit son prompt à partir du statut du profil. « Disponible pour missions et CDI » le faisait répondre quelque chose de faux à un recruteur qui demandait si je cherchais un stage.
3. **Pourquoi des variables factices pour le build ?**
   Le build Next.js collecte les données des pages et le client Supabase refuse de s'initialiser sans URL. Des valeurs factices, passées seulement au shell, permettent de vérifier que le code compile et que les pages se génèrent, sans secret sur le disque ni dans le dépôt.
4. **Quel risque prenait-on en poussant sur `main` ?**
   Vercel déploie automatiquement chaque push sur `main` : un build cassé aurait laissé le site sur l'ancienne version, mais un bug d'exécution aurait été en production. D'où la règle : build local vert avant push, et changement limité à des chaînes de texte.
5. **Comment vérifier que la modification est bien en production ?**
   Statut du déploiement Vercel sur le commit (« success »), puis lecture du HTML servi : la balise `meta name="description"` contient le nouveau texte.
